# ADR 0011: Module-first организация модульного монолита

**Статус**: Заменено [ADR 0012](0012-strict-modular-monolith.md)
**Дата**: 2026-08-05

## Контекст

Backend FundingMonitor разделён на проекты `Core`, `Application`, `Infrastructure` и `Api`. По мере развития сбор текущих и исторических ставок превратился в два самостоятельных бизнес-процесса, но связанные с ними классы были распределены по общим техническим каталогам `Entities`, `Services`, `Repositories` и `Controllers`. Навигация по коду стала сложнее.

Разделение на микросервисы не требуется: приложение развёртывается как один процесс, использует одну PostgreSQL database и единый HTTP API.

## Решение

Сохраняем четыре проекта Clean Architecture, но внутри каждого проекта группируем код сначала по бизнес-модулю:

- `CurrentRates` — текущие ставки, staleness, обнаружение изменений и арбитраж;
- `HistoricalRates` — исторический сбор, RabbitMQ consumers, retry/DLQ, хранение истории и APR;
- `Shared` — общие exchange contracts и clients, `FundingMonitorDbContext` и общая HTTP infrastructure.

Каждый модуль имеет собственный namespace и собственную точку регистрации зависимостей. `Program.cs` явно собирает `Shared`, `CurrentRates` и `HistoricalRates`.

Связь модулей направленная: `CurrentRates` публикует `HistoricalCollectionTask`, а `HistoricalRates` обрабатывает её через RabbitMQ. Модули не обращаются к внутренним collectors или repositories друг друга.

Приложение, схема базы данных, API routes и runtime-поведение не изменяются.

## Последствия

Преимущества:

- связанный бизнес-код проще находить;
- границы current и historical collection видны в каталогах, namespaces и DI;
- существующие Clean Architecture layers и deployment model сохраняются;
- последующий переход к отдельным module assemblies возможен без предварительного выделения микросервисов.

Недостатки:

- границы каталогов не обеспечивают полную compile-time isolation;
- общий `FundingMonitorDbContext` и exchange clients остаются точками совместного использования;
- правила зависимостей требуется защищать архитектурными тестами и code review.

## Альтернативы

### Оставить только layer-first структуру

Не выбрано, потому что именно распределение одного бизнес-процесса по общим техническим каталогам ухудшило навигацию.

### Создать отдельную сборку для каждого модуля

Даёт compile-time контроль зависимостей, но сейчас добавляет лишние `.csproj` и усложняет composition root. Вариант будет оценён после эксплуатации лёгкой модульной структуры.

### Создать отдельную сборку для каждого слоя каждого модуля

Обеспечивает наиболее строгую изоляцию, но для текущего размера проекта создаёт непропорциональное количество проектов и boilerplate.
